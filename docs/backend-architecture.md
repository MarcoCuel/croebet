## Arquitetura

- `apps/web`: Next.js App Router, React e interface; consulta Fastify por HTTP no carregamento inicial e usa Socket.IO nas interações multiplayer. [Frontend](frontend-architecture.md).
- `apps/api`: monólito modular Fastify/Node/TypeScript; PostgreSQL com Drizzle + `pg`. Rotas em `src/modules/auth/routes.ts` e `src/modules/admin/routes.ts`; serviços junto ao domínio.
- `packages/shared/src`: schemas Zod de entrada/saída e tipos públicos; validar em runtime, não apenas por tipos TypeScript. Contratos exatos ficam no código.
- `apps/api/src/db/schema.ts` e `apps/api/drizzle`: estrutura e migrations; `src/db/cli.ts`: migrate, seed e reset.
- HTTP em `/api/v1`; Next encaminha esse prefixo para `API_INTERNAL_URL` (padrão `http://127.0.0.1:3001`). É proxy de transporte, sem backend de domínio no Next.
- Docker inicialmente só para PostgreSQL 18. Web e API rodam como processos Node no host. Não adicionar microsserviços, Redis, filas externas ou workers separados sem necessidade concreta.
- Multiplayer usa Socket.IO em `/api/v1/realtime`, com transporte WebSocket, sem barra final e pelo mesmo proxy. O cliente compartilha a conexão entre mesa/lobby e convites. O cliente busca CSRF antes de abrir o WebSocket, inclusive nas reconexões, para que o cookie do upgrade corresponda ao token. O handshake exige Origin, sessão e CSRF; o transporte delega comandos ao mesmo serviço transacional das rotas HTTP, sem executar regras.

## Ambiente local

Use Node compatível com `engines` e o pnpm fixado em `packageManager` na raiz; Docker Desktop iniciado. API em desenvolvimento executa TypeScript com `--experimental-strip-types`: mantenha sintaxe compatível com `erasableSyntaxOnly`.

1. Copie `.env.example` → `.env`, `apps/api/.env.example` → `apps/api/.env` e `apps/web/.env.example` → `apps/web/.env.local`.
2. Defina `POSTGRES_PASSWORD` na raiz e monte `DATABASE_URL` da API com os mesmos usuário, senha, banco e porta. Defina `APP_ENV=development`, `WEB_ORIGIN=http://localhost:3000` e `CSRF_SECRET` aleatório de pelo menos 32 caracteres. Exemplos de variáveis ficam nos `.env.example`; não versione segredos.
3. Instale e prepare a base:

```sh
pnpm install --frozen-lockfile
pnpm db:up
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Acesse `http://localhost:3000`; API em `127.0.0.1:3001`. `GET /api/v1/health` verifica o processo; `/api/v1/health/ready` verifica conexão e marcador do ambiente, não substitui a aplicação das migrations.

| Comando na raiz | Uso |
| --- | --- |
| `pnpm dev:web` / `pnpm dev:api` | Iniciar aplicações separadamente |
| `pnpm db:up` / `pnpm db:stop` / `pnpm db:logs` | Iniciar, parar ou acompanhar PostgreSQL |
| `pnpm db:generate` / `pnpm db:migrate` | Gerar/aplicar alterações de schema |
| `pnpm db:seed` | Identificar ambiente e cadastrar Flip 7 sem sobrescrever edições |
| `pnpm db:reset` | Recriar schema e executar migrations/seed no destino autorizado |

Compose publica PostgreSQL somente em `127.0.0.1`, com volume persistente. Alterar `POSTGRES_*` não reconfigura um volume já inicializado. Páginas, cupons, usuários e apostas não recebem dados de exemplo pelo seed; a navegação inicial é criada pela migration de menus.

### Testar no celular pela rede local

O Next dev já escuta em `0.0.0.0:3000`. Mantenha a API em `API_HOST=127.0.0.1` e `API_INTERNAL_URL=http://127.0.0.1:3001` no web: o proxy `/api/v1` atende HTTP e Socket.IO, sem abrir a porta da API para a rede.

No Mac, identifique a interface da LAN com `route -n get <IP-do-roteador>` e consulte seu IPv4 com `ipconfig getifaddr <interface>` (a rota padrão pode apontar para uma VPN). Adicione `DEV_WEB_ORIGINS=http://<IP-do-Mac>:3000` tanto em `apps/api/.env` quanto em `apps/web/.env.local`, preservando `WEB_ORIGIN=http://localhost:3000`. Reinicie web e API (`pnpm dev` ou os comandos separados) e abra esse endereço no celular conectado à mesma LAN. Se o IP mudar, atualize os dois arquivos e reinicie novamente. Os arquivos locais de ambiente são ignorados pelo Git.

A API aceita somente origens exatas configuradas, com CSRF obrigatório; produção rejeita `DEV_WEB_ORIGINS` e continua com uma única origem HTTPS. O Next libera os hostnames adicionais apenas no servidor de desenvolvimento. Cookies permanecem HttpOnly, SameSite=Lax e host-only: faça login separadamente em localhost e no IP. Os IDs das ações usam aleatoriedade criptográfica também em HTTP na LAN. A cópia automática de links depende da permissão de clipboard do navegador e pode não estar disponível sem HTTPS.

Se o celular não alcançar o site, verifique se o firewall permite conexões ao Node, se o Wi-Fi isola clientes e se a VPN permite tráfego local. Não exponha a API nem desative CSRF para contornar problemas de rede.

Registra commit e estado da árvore em `release.json`; não faz pull, commit nem merge. Instala dependências com lockfile e constrói a nova release antes de interromper produção. Alterações posteriores no dev não mudam o código que já está rodando. Também é possível operar sem o dev: `node /Users/marco/Desktop/croebet-production/current/scripts/production.mjs status` (ou start, stop, logs, backup, rollback).

O deploy permite partidas em andamento: a release candidata valida jogo, versão de regras, opções e snapshots privados de todas as salas ativas com seus próprios drivers, antes de parar e novamente após drenar a API. Incompatibilidade recusa a publicação; ao alterar regras ou formatos, preserve suporte à versão em uso até a conclusão das mesas. O verificador é `modules/matches/deployment.ts`; ele não executa jogadas nem expõe estados privados. Parada manual, backup isolado e rollback de código continuam recusando qualquer partida em andamento sob o lock de ciclo de vida.

Build e instalação ocorrem enquanto a versão anterior atende. Na troca há uma interrupção: a API deixa de aceitar trabalho Socket.IO, fecha o transporte para disparar reconexão e aguarda as operações aceitas terminarem. O deploy só adquire o advisory lock de ciclo de vida após drenar a API, evitando prender comandos de início/abandono que precisam do mesmo lock. Banco e imagens são copiados juntos em `backups/<identificador>`. Migrations são ensaiadas em uma cópia exclusiva de test; além de contagens e saldos, confere-se o digest dos estados, versões, regras e opções das salas ativas e sua compatibilidade com a candidata. As mesmas verificações são repetidas no banco real antes de ativar a release. Somente a cópia descartável de test pode ser removida, após conferir marcador, nome e destino com as proteções existentes. O banco real nunca é resetado, recriado ou limpo pelo deploy.

Partidas e lobbies permanecem persistidos, sem abandono ou devolução causados pelo reinício. Reconectar renova presença e recupera o estado confirmado; repetir uma jogada usa seu recibo idempotente. O frontend recebe o identificador público da release no build/runtime, configura `deploymentId` do Next e oferece atualização mantendo a URL da mesa. A retomada de escolhas ainda não enviadas não é garantida. O processo atual usa reinício controlado, sem garantia de disponibilidade contínua durante backup, ensaio e migrations.

Falha após parar, mas antes de iniciar migrations reais, reinicia a release anterior com o schema ainda intacto. A partir das migrations reais, falhas deixam produção parada e backups preservados para análise; nunca restauram dados automaticamente. Consulte logs, `shared/installation.json` e a última release, corrija a causa e repita `prod:deploy` ou `prod:start` quando a compatibilidade estiver confirmada. Instalação com estado `preparing` exige recuperação da etapa interrompida, sem repetir restore sobre um banco preenchido. O diretório `.operation-lock` serializa operações; após interrupção abrupta, verifique o PID registrado antes de remover somente esse lock. Não remova volumes, backups ou releases para resolver um lock.

Recuperação de dados: mantenha as aplicações paradas; selecione um backup completo (dump, imagens, configurações e manifesto), restaure primeiro em um PostgreSQL vazio e isolado usando `pg_restore --no-owner --no-acl --exit-on-error`, confira contagens/saldos, imagens e marcador, recrie a credencial runtime e suas permissões. Teste com uma release compatível antes de trocar o destino. Preserve o volume anterior para investigação. Restaurar backup reverte ações posteriores ao ponto escolhido: exige decisão operacional explícita, conciliação dos lançamentos e auditoria, nunca uma ação automática de rollback. `prod:rollback` troca somente o código; use-o apenas se a versão anterior aceitar o schema atual.

### Compartilhar produção pelo túnel

A rota pública `croebet.marcocuel.com` do túnel gerenciado deve apontar para **`http://127.0.0.1:6767`**. Não publicar a API, o PostgreSQL nem o dev. A credencial fica somente em `croebet-production/shared/tunnel-token` (arquivo 600). Salve somente o token do túnel específico da Croebet nesse arquivo e use `prod:start`. Não reutilize automaticamente tokens de serviços globais: eles podem pertencer a outro site. O supervisor de produção inicia `cloudflared` após web/API ficarem prontas. Sem token, a produção local pode iniciar, mas o acesso público fica pendente. Se já houver um conector instalado como serviço do macOS, confira e evite executá-lo em duplicidade; a ferramenta não altera serviços globais nem outros sites.

O frontend de produção redireciona solicitações HTTP para `https://croebet.marcocuel.com`, preservando caminho e query. O protocolo do visitante vem de `X-Forwarded-Proto` enviado pela Cloudflare, evitando loop com o HTTP local do túnel; a porta local é acessível somente em loopback. Health checks locais são exceções. Também pode ser usada uma regra de redirecionamento na Cloudflare restrita a esse hostname; não habilitar uma mudança global que afete outros sites sem verificar suas configurações. Referências: [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/) e [redirecionamento HTTPS](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/always-use-https/).

HTTP e WebSocket (`/api/v1/realtime`, sem barra final) passam pelo proxy do Next para `6768`. `API_INTERNAL_URL` é definido no build e no runtime da release; Origin/CSRF/sessões Secure continuam validados pela API. Em produção, `TRUST_CLOUDFLARE_PROXY=true` permite identificar visitantes por `CF-Connecting-IP` somente se a conexão da API vier de loopback; o header é sobrescrito pela Cloudflare na borda. O Next também precisa estar restrito a loopback. Limites por IP de cadastro/login e conexões anônimas usam esse endereço e não somam sessões de contas autenticadas; sem a configuração, headers de IP são ignorados. Não configurar cache de HTML/API autenticada ou bloquear o upgrade WebSocket no túnel. Reconexões recuperam estados/eventos confirmados do PostgreSQL. O Mac deve permanecer acordado, com Docker e produção ativos; os comandos não instalam inicialização automática após reboot. Logs ficam em `shared/logs` (produção) e `.data/development/logs` (dev); nunca compartilhar logs ou backups sem revisar dados privados.

### Preservação de dados e reset

O projeto está em operação com usuários reais. Preserve contas, economia, partidas e auditoria; use migrations incrementais, sem consolidar migrations aplicadas. Antes de implantar alterações no banco real, mantenha backup recuperável e valide a migration em uma cópia isolada. Não execute reset ou limpeza destrutiva para implementar funcionalidades.

`db:reset` é exclusivo de bases locais descartáveis explicitamente autorizadas e de test. Exige `APP_ENV=development|test`, `NODE_ENV` diferente de `production`, marcador compatível, `DB_RESET_ALLOWED_URL` exata e `DB_RESET_CONFIRM` igual ao banco. Produção recusa reset e exige credencial separada de migration. Uma base marcada como development pode conter dados reais: o marcador não autoriza seu descarte.

## Conta e autorização

O onboarding usa `users.profile_name_provided` para distinguir nome informado do username atribuído automaticamente no cadastro, e a presença de `avatar_key` para a foto. A projeção privada de sessão retorna `onboarding` com esse indicador e `remindAt`; o perfil público não expõe o adiamento. `POST /me/onboarding/defer` exige sessão, Origin/CSRF e grava 12 horas a partir do relógio do PostgreSQL, revalidando sessão e conta sob lock. `PATCH /me/profile` marca o nome como informado mesmo quando coincide com o username. O onboarding permanece pendente enquanto faltar nome informado ou foto, inclusive se a foto for removida depois.

Implantação do onboarding: aplicar `0032_profile_onboarding.sql` antes de atualizar API/web, com backup recuperável e validação em banco isolado. A migration preserva os dados e reconhece como informado o nome existente que difere do username; nomes iguais não permitem distinguir a atribuição automática e serão solicitados novamente. O prazo começa nulo. Em rollback da aplicação, manter as colunas e seus dados; não reverter migrations anteriores.

- Username preservado, unicidade/login sem distinguir caixa; nome de exibição independente. Regras de produto em [CROEBET.md, seção 3](../CROEBET.md#3-público-e-acesso); limites exatos nos schemas compartilhados. Senha com Argon2id; sem e-mail ou recuperação implementados. `PATCH /me/password` exige senha atual, valida a nova senha e limita tentativas; revalida hash, conta e sessão dentro da transação, altera o hash e revoga as outras sessões, preservando a atual. Login revalida o hash antes de emitir sessão para impedir autenticação concorrente com senha substituída.
- Sessão opaca aleatória em cookie HttpOnly, host-only, SameSite=Lax; apenas hash no banco. Expiração absoluta de 30 dias e inatividade de 7 dias. Em `APP_ENV=production`, usa Secure e prefixo `__Host-`.
- Toda mutação exige Origin na lista explícita (`WEB_ORIGIN` e extras apenas em development/test) e token CSRF ligado à sessão/nonce, inclusive pré-login. Limites de tentativas são persistidos. Não registrar senhas, cookies ou tokens.
- Papéis `user` e `admin`, conferidos pela API. Sem acesso administrativo: 404. A renderização do Next não substitui autorização no serviço; revalide sessão/conta dentro da transação de escrita.
- Nenhum cadastro, nome ou variável pública concede admin. A primeira promoção é operacional no banco de desenvolvimento; depois, Admin → Usuários gerencia papéis. Não há conta/senha administrativa no seed.
- Alterar papel/status ou excluir conta usa lock de governança antes dos locks de usuário/sessão/carteira; não pode remover o último admin ativo. Suspender revoga sessões; reativação exige login.
- Exclusão pela própria conta exige senha e remove identidade/sessões; carteira fica desvinculada e auditoria permanece, conforme as FKs e invariantes atuais. Históricos administrativos das partidas permanecem independentes da conta excluída.

Admin → Usuários agenda exclusão em 30 dias (`DELETE /admin/users/:id`): suspende imediatamente, revoga sessões e audita na mesma transação. Pedidos repetidos mantêm o prazo. Reativar pelo status cancela o agendamento; suspensão comum não agenda exclusão. O último administrador ativo continua protegido. A API processa lotes vencidos ao iniciar e a cada minuto, usando o relógio do PostgreSQL, lock de governança e validação do ambiente; falhas revertem e são retentadas. Remove identidade/sessões e salas operacionais, agenda limpeza de avatar e preserva carteira desvinculada, auditoria e arquivos de partidas.

Implantação: aplique a migration incremental `0024_odd_hydra.sql` antes de atualizar API/web; contas existentes recebem prazo nulo. Preserve backup antes da implantação. Para interromper a limpeza, pare os processos da API; durante os 30 dias, reativar a conta cancela o prazo. Após a exclusão definitiva, recuperar identidade exige restauração controlada de backup. Em rollback de aplicação, mantenha a coluna para não perder agendamentos; não reverta migrations anteriores.

O perfil público retorna identidade e um calendário do último ano em `America/Sao_Paulo`, ampliado até o início do primeiro mês e da primeira semana para evitar recortes no começo. A API agrega partidas concluídas do arquivo, recibos de bônus diário e cupons, incluindo dias vazios. Cada evento vale uma atividade; vitórias (incluindo empates na maior pontuação, sem bot no resultado) são apenas detalhes. Partidas em andamento/abandonadas e ações administrativas não contam. O histórico usa exclusivamente os registros disponíveis, sem inventar eventos anteriores, e não expõe códigos de cupons, valores, IDs ou estados das partidas. Não requer migration; a agregação acompanha o histórico persistido.

O perfil também oferece `GET /profiles/:username/matches`, público e paginado, reutilizando a consulta do histórico da conta com apenas partidas concluídas/encerradas da pessoa, da mais recente para a mais antiga. Retorna nome/capa do jogo, descrição e data, sem movimentações financeiras, códigos de sala, links de replay ou estados do motor; contas inexistentes/inativas retornam 404. Não requer migration.

O histórico privado em `GET /me/history` reúne lançamentos da carteira (incluindo bônus e cupons) e partidas concluídas/encerradas em que a conta participou, com paginação e ordem cronológica decrescente. Usa os registros existentes, sem migration ou cópia de eventos. Retorna descrição, data, tipo e valor quando houver movimentação; entradas de partidas incluem `matchId`, código e slug do jogo para abrir o endereço original. `GET /me/matches/:code` exige sessão e participação no arquivo de uma partida concluída/encerrada; sem acesso responde 404 antes de consultar frames. Retorna apenas as projeções públicas já arquivadas, com snapshot público final, paginação de frames, resultado e liquidação, reutilizando a leitura do admin. Funciona após remoção da sala, sem depender da ativação do jogo e sem migration.

### Avatares

API recebe JPG/PNG/WebP, valida e reprocessa com Sharp para WebP 256 × 256 sem metadados (limites em `modules/avatars/image.ts`). Banco guarda chave aleatória; perfil/sessão retornam apenas URL pública. Desenvolvimento usa arquivos locais; a produção independente no Mac usa diretório persistente separado e absoluto, com opt-in explícito. O adaptador S3 privado continua disponível, configurado pelos `.env.example`.

Leitura pela API revalida o vínculo com conta ativa antes de servir ou responder 304; usa ETag e `private, no-cache`. Substituição/remoção agenda limpeza persistida; o próprio processo retenta a fila ao iniciar e a cada minuto. Credenciais e caminhos de armazenamento ficam exclusivamente na API.

## Carteira e recompensas

Regras e valores aprovados estão em [CROEBET.md, seção 4.3](../CROEBET.md#43-croins-economia-fictícia); a configuração executável fica em `modules/economy/config.ts` e é publicada por `/api/v1/economy`. Frontend não mantém valores econômicos alternativos.

- `wallet_accounts`, `wallet_operations`, `wallet_entries`: livro imutável com lançamentos de soma zero, contas de emissão/casa/pote/usuário e saldo aplicado por triggers. Correções de domínio geram contrapartidas; não editam lançamentos.
- Croins inteiros: PostgreSQL BIGINT/BigInt nos cálculos; contratos públicos limitados à faixa inteira segura de JavaScript. Contas de usuário/pote/casa não ficam negativas; emissão financia concessões explicitamente.
- `transferCroinsInTransaction(client, input)` participa da transação do domínio: chamador autoriza, bloqueia recursos e controla begin/commit/rollback. Recibo só é definitivo após commit. `transferCroins(pool, input)` gerencia uma transação própria; nenhum dos dois é endpoint público de transferência.
- Locks em ordem consistente; chave idempotente por escopo vinculada ao conteúdo. Retry retorna recibo original; mesma chave com conteúdo diferente é conflito. Saldo, recibo, registro de domínio e auditoria confirmam juntos.
- Cadastro concede bônus junto à criação da conta/carteira/sessão. Resgate diário usa o relógio do PostgreSQL e a meia-noite de `America/Sao_Paulo`, sem limite de saldo; unicidade e `requestId` impedem duplicação. Não há backfill para contas antigas.
- Cupons: código normalizado em maiúsculas, valor positivo obrigatório, limite global e datas opcionais, pausa e um uso por conta. Início inclusivo/término exclusivo. Limites, validade, recibo e crédito são conferidos na mesma transação; histórico guarda código/valor efetivamente concedidos.
- Motivo é opcional nas ações administrativas. Ausência de motivo no ajuste usa a descrição padrão; a exigência interna de descrição do livro não cria campo obrigatório na interface.
- `/me/wallet` e `/me/transactions` são autenticados; extrato paginado e filtrado na API, sem carteira local alternativa.

## Conquistas

`modules/achievements` agrega arquivos de partidas, liquidações, bônus e cupons. `GET /me/achievements` exige sessão; em uma transação, revalida conta/sessão, consulta métricas históricas e concede níveis ativos com unicidade por conta/nível. Repetições mantêm os desbloqueios e suas datas. A maior sequência histórica não cai quando a sequência atual é interrompida. Não há alteração de saldos nem importação do protótipo. Critérios em [Rankings e gamificação](../CROEBET.md#44-rankings-e-gamificação).

`/admin/achievements` e `/admin/achievements/:id` reutilizam autorização, CSRF, limite de escrita, transação administrativa, versão otimista e auditoria. Um lock compartilhado de catálogo permite conciliações de contas distintas; escritas administrativas usam o lock exclusivo. Conciliações de uma mesma conta são serializadas. Metas/remoções de níveis concedidos e trocas do critério com concessões são recusadas; desativar preserva o histórico. As metas usam inteiros seguros e crescentes, sem limite fixo de níveis; os limites normais de tamanho da requisição continuam aplicáveis.

O emblema opcional é salvo em `achievement_definitions.image_url`, selecionado da biblioteca e validado na transação administrativa; referências de conquistas, inclusive inativas, impedem exclusão da imagem. A migration incremental `0034_achievement_emblems.sql` deve ser aplicada antes da API/web: acrescenta somente a coluna com valor vazio para preservar o ícone atual. Em rollback, mantenha a coluna e as imagens, sem reverter dados.

Cores opcionais em `achievement_definitions.color` e `achievement_levels.color` aceitam somente hexadecimal de seis dígitos; `achievement_levels.image_url` permite emblema próprio por nível, validado e protegido contra exclusão pela biblioteca, inclusive em conquistas inativas. Personalização de níveis concedidos preserva metas, IDs e datas de desbloqueio. A migration incremental `0041_past_princess_powerful.sql` acrescenta essas colunas sem reescrever concessões; aplique antes de publicar API/web e mantenha as colunas ao recuar a aplicação. Valores nulos/vazios herdam os padrões existentes.

A migration `0028` adiciona catálogo, níveis e concessões, com seis definições iniciais editáveis. Aplicar antes de publicar API/interface; não requer reset, seed de contas nem reescrita do livro/arquivos. Para recuar a aplicação, desabilitar o acesso à funcionalidade e manter as tabelas/concessões, sem reversão destrutiva. Exclusão de conta remove seu progresso privado via FK; os históricos independentes de partidas/economia permanecem preservados.

## Conteúdo e administração

- Mesa 3D: `GET /api/v1/table-visual-settings` fornece somente o preset visual global e sua versão, sem cache; `PATCH /api/v1/admin/table-visual-settings` exige admin/CSRF e versão esperada, persiste e audita atomicamente. Contrato em `shared/table-visual-settings.ts`; jogadores, mãos, visibilidade e estado dos jogos são rejeitados. Aplicar a migration incremental `0036_lazy_nightshade.sql` antes de implantar a API. Ela acrescenta apenas a tabela singleton `table_visual_settings`, sem alterar dados existentes; ausência de preset usa os padrões compartilhados. Em recuperação, preservar a tabela e a auditoria; rollback da aplicação pode manter a tabela adicional.

- Escritas administrativas usam sessão/papel, CSRF, limites, transação e auditoria atômica. Recursos editáveis têm versão esperada ou estado anterior esperado; conflito não sobrescreve outra edição.
- Usuários: admin edita nome de exibição e username por `/admin/users/:id/identity`, com schemas compartilhados, valores anteriores esperados, locks e auditoria na mesma transação. Unicidade do username continua case-insensitive. Correção administrativa não espera o intervalo de 30 dias, mas uma mudança efetiva de username reinicia esse intervalo para a edição pela própria conta. Permissão/status continuam no fluxo existente, com proteção do último admin e revogação de sessões ao suspender.
- Senha de usuários: `PATCH /admin/users/:id/password` permite ao admin definir uma nova senha de 8 a 128 caracteres sem a senha anterior. Usa Argon2id, limite de tentativas, revalidação de autorização e conflito de alteração concorrente; atualização, revogação de sessões e auditoria ocorrem na mesma transação. Não inclui senha ou hash na resposta/auditoria. Ao editar a própria conta, preserva somente a sessão atual; em outra conta, revoga todas as sessões. Não exige migration.
- Internas e endpoints administrativos identificam entidades existentes por UUID (`/admin/paginas/[id]`, jogos, apostas, usuários e cupons). Slug fica nos endereços públicos; mudar slug não cria alias histórico de páginas. Jogos registrados mantêm o identificador do módulo como endereço de compatibilidade para convites e replays. `nova`/`novo` são ações de criação, não IDs de entidades.

Maiúsculas, acentos e espaços são aceitos na edição; endereços vazios, reservados em páginas ou acima do limite continuam inválidos. Consultas públicas exigem formato canônico, e a unicidade continua sendo conferida no banco, sem alterar endereços já cadastrados.
- Páginas: documento JSON validado em `shared`, sem HTML arbitrário; autoria, datas, versão, status editorial e lixeira. Agendamento vencido é resolvido nas consultas pelo relógio do banco, sem scheduler em memória. Restaurar lixo retorna a rascunho; exclusão definitiva é auditada.
- Menus `main` e `footer` independentes, planos e ordenados. Destinos: página fixa, UUID de página criada ou URL validada. Publicação não adiciona item ao menu; referências por UUID acompanham o slug. Destinos não públicos são omitidos. `showInMenu` ainda existe no contrato de páginas, mas não determina a navegação.
- Ícone de menu é opcional, validado pelo catálogo Lucide; sem escolha, sem ícone. API resolve apenas os vetores dos ícones escolhidos. Ao atualizar `lucide-react`, execute `node scripts/sync-lucide-icons.mjs`; não enviar vetores arbitrários na escrita.
- Duração dos jogos: o catálogo público informa a média em segundos de partidas concluídas com duração positiva, primeiro dos arquivos oficiais, depois dos testes e, sem amostras válidas, do valor manual em minutos no editor do jogo. Testes somente com bots usam o tempo de reprodução acumulado; os demais usam início/fim. Arquivos são agregados uma única vez por partida, inclusive após exclusão de conta; partidas abandonadas ou sem tempo válido não entram. Aplicar `0037_nervous_sharon_ventura.sql` antes da API: acrescenta somente a coluna opcional `games.fallback_duration_minutes` e sua restrição (1–10.080). Preserva registros existentes; rollback da aplicação pode manter a coluna e os valores. Escrita mantém versão esperada e auditoria na mesma transação.
- Jogos: painel cria registros do catálogo e edita nome, descrição em texto simples (opcional, até 2.000 caracteres), ativação e capa selecionada na biblioteca de mídia. URLs/caminhos de capa já cadastrados continuam válidos. Criação usa `/admin/games` (POST), slug único validado e auditoria na mesma transação; o slug pode ser alterado na edição, sem mudar o `module_id` que identifica o motor. `DELETE /admin/games/:id` exige versão e registra exclusão lógica auditada: retira o jogo das listagens, desativa novas partidas e conserva UUID, históricos, saldos e referências. Salas ou partidas em andamento impedem a exclusão; consultas administrativas por UUID e replay permanecem disponíveis. Slugs excluídos continuam reservados. Aplicar `0038_dizzy_jigsaw.sql` antes da API: adiciona `module_id` e `deleted_at`, preenche os módulos existentes sem alterar slugs ou referências. Fazer backup antes da implantação; em recuperação, preservar as colunas e registros. Rollback para uma aplicação que ignora `deleted_at` pode reexibir jogos excluídos no admin; versões que dependem do slug para escolher o motor também precisam de compatibilidade com jogos renomeados. Prefira corrigir a aplicação mantendo a migration. Aplicar a migration incremental `0025_redundant_gorgon.sql` antes de implantar a API; ela amplia a restrição de slug preservando registros e referências. Em recuperação, manter essa restrição e os registros criados; versões antigas que aceitam apenas `flip7` precisam da compatibilidade de catálogo antes de um rollback de aplicação.

- SEO: `/admin/seo` persiste padrões e ajustes de Home/Jogos; páginas e jogos têm campos opcionais próprios. Escrita com versão e auditoria. API pública desativa indexação fora de `APP_ENV=production`; sitemap inclui somente conteúdo público indexável.

### Biblioteca de mídia

Admin → Mídia (`/admin/midia`) lista, busca, envia, visualiza e exclui imagens por `/admin/media`. Metadados em `media_assets`; URLs públicas estáveis em `/api/v1/media/:uuid.webp`. Upload binário JPG/PNG/WebP de até 10 MB e 25 megapixels, estático, reprocessado com Sharp para WebP sem metadados, mantendo proporção/transparência e limitando o maior lado a 4096 px. Nome original, título e descrição editáveis, dimensões, bytes, autor e data ficam no PostgreSQL; objetos nunca são listados pelo bucket.

Reutiliza o adaptador local/S3 dos avatares, as variáveis `AVATAR_STORAGE`/`S3_*` e o mesmo bucket privado, com prefixo separado `media/`. Localmente usa a pasta `media` ao lado de `AVATAR_LOCAL_DIR`; avatares mantêm seu diretório, prefixo, permissões e limpeza próprios. A API serve o objeto sem expor credenciais. Leitura pública verifica registro ativo antes de servir ou responder 304; cache exige revalidação.

Envio/exclusão exigem admin, CSRF, limite de tentativas e revalidação transacional de sessão/papel; confirmação e auditoria são atômicas. Upload começa como `uploading`, só aparece após confirmação `ready`; exclusão marca `deleted` e oculta imediatamente. Limpeza persistida remove objetos excluídos e uploads incompletos após uma hora, com retentativa no ciclo existente da API. Exclusão recusa referências de emblemas de conquistas, capas/SEO de jogos, SEO de páginas (inclusive rascunhos/lixeira), configurações e links de menus. Escritas dessas áreas validam referências da biblioteca sob o mesmo lock administrativo da exclusão, evitando salvar seleções excluídas em formulários abertos. URLs antigas externas/estáticas são preservadas sem importação automática.

Implantação: faça backup e aplique as migrations incrementais pendentes, incluindo `0042_slow_captain_stacy.sql`, antes de atualizar API/web. A migration 0042 acrescenta título e descrição vazios sem alterar os arquivos existentes. A migration só acrescenta tabela, índice e restrições; não altera imagens ou dados existentes. Em rollback de aplicação, mantenha a tabela e os objetos: versões antigas continuam lendo suas URLs enquanto a API que serve mídia permanecer disponível; recuperação exige restabelecer API compatível e os backups de banco/bucket, sem reverter migrations antigas.

## Chat geral

O chat exige conta ativa e usa `modules/chat/routes.ts` dentro dos hooks de sessão, Origin/CSRF, ambiente e cache da autenticação. `GET /api/v1/chat` entrega as últimas 50 mensagens e paginação por ID; `/chat/sync?after=` recupera eventos confirmados em lotes. Envio aceita texto simples de até 500 caracteres e `requestId` idempotente; a API impõe intervalo de dois segundos e até vinte mensagens por minuto, além do limite de requisições por conta.

A migration `0033_slimy_gamora.sql` acrescenta mensagens, silenciamentos e eventos, sem modificar dados existentes. Aplicar com o fluxo normal de migrations antes de usar o chat; rollback da aplicação pode manter essas tabelas, preservando a conversa. Escritas são serializadas por advisory lock transacional para que os cursores sigam a ordem de commit. Uma leitura inicial usa snapshot consistente; reconexões percorrem os eventos pendentes. `LISTEN croebet_chat`, no transporte Socket.IO existente, transmite somente um sinal aos usuários autenticados; histórico e conteúdo vêm de consultas HTTP autorizadas. A sincronização automática valida a sessão sem renovar seu prazo ocioso. Não mistura comandos ou estados privados dos motores.

Admin pode remover mensagens ou silenciar por 10 minutos, uma hora ou 24 horas e desfazer o silenciamento. Remoção pública retorna um marcador sem texto; conteúdo original e autor da moderação permanecem no banco para auditoria, sem endpoint público de acesso. Eventos de silenciamento registram responsável, destinatário e prazo. Exclusão de conta mantém as mensagens com identidade pública “Conta excluída”, sem FK que impeça excluir a conta. Não há anexos, mensagens privadas ou interpretação de HTML/Markdown.

## Base compartilhada dos jogos

Os jogos são módulos revisados no repositório. O registro público em `packages/shared/src/game-registry.ts` declara configurações, limites e capacidades; `modules/games/registry.ts` liga cada identificador ao seu driver na API. Flip 7, Love Letter e Solo usam o mesmo executor, autorização, recibos, locks, persistência e transporte. O catálogo administrativo não instala código: um cadastro sem módulo registrado continua em desenvolvimento.

| Responsabilidade | Contrato e limites |
| --- | --- |
| Sessão de conta | Reutilizar autenticação existente, suspensão e revogação. Sessão de login é distinta de partida/sala; reconectar não cria participação nem cobra entrada. |
| Partidas e participantes | Identidade da partida, jogo/modo/versão de regras, ciclo de vida, vagas vinculadas a contas, versão do estado e datas. Não exigir lobby, turnos ou múltiplos jogadores de todos os jogos. |
| Comandos | Envelope com partida, `commandId`, `expectedVersion` e ação validada pelo jogo; executor comum autoriza participação, bloqueia, deduplica e persiste. Comandos HTTP e Socket.IO chegam ao mesmo executor; eventos Socket.IO apresentam estados já confirmados. |
| Estado e recuperação | Snapshot privado validado pelo motor, eventos ordenados e projeção por destinatário. O motor define o que cada jogador/espectador pode ver; não enviar o estado inteiro ao cliente. |
| Resultados e histórico | Registro comum de conclusão/participantes, com resultado validado por jogo. Pontuação e estatísticas são específicas: não exigir pontos de roleta/caça-níqueis nem comparar pontos de jogos diferentes. Pontos, vitória e prêmio em Croins são conceitos separados. |
| Economia | Reutilizar o livro e seus recibos/transações; entrada, pote, devolução e prêmio vinculados à partida. Motor produz resultado, não altera saldo diretamente. Cada modalidade define financiamento e distribuição antes de habilitar Croins. |
| Automações | Executor persistente comum para trabalho vencido; motor define bots, compras obrigatórias e próxima decisão. Prazo, controle da decisão e política de desconexão dependem do jogo. |
| Aleatoriedade e cartas | Fonte aleatória segura/injetável reutilizável. Baralho, reposição, descarte, informação oculta e efeito de comprar pertencem ao jogo; extrair utilitários puros de cartas quando houver segundo uso concreto. |

`modules/matches/driver.ts` define o contrato de integração. Cada módulo implementa criação, validação do snapshot privado, transição, automação, decisão humana, substituição por bot, projeção pública/por destinatário, resultado e resumo do histórico. O executor não interpreta regras, modalidades, pontuação ou campos privados. Valores `unknown` na fronteira do registro passam pelos parsers concretos do módulo; não são estados livres de validação. O motor não acessa banco, carteira, HTTP ou React.

`match-contracts.ts` reúne envelopes comuns; `game-compatibility.ts` mantém schemas concretos dos clientes existentes. Os schemas de opções, ações e projeções registrados devem ser incluídos nas uniões validadas do registro. Não adicionar ramificações por identificador ao serviço de partidas.

“Pedir carta” é uma ação do jogo, transportada pelo envelope comum, não um endpoint genérico que permite retirar qualquer carta de qualquer baralho. No Flip 7 ela pode estourar, ativar proteção ou abrir escolha de alvo; no blackjack terá outras condições e efeitos. Estado privado e payload de ação mantêm schemas Zod específicos/discriminados por jogo, sem `any` ou JSON sem validação. Tipos atuais `Game`, `Card`, `Player` e a fórmula `score` do Flip 7 não são contratos universais.

Sessão e carteira já existem; não recriá-las por jogo. As rotas de partidas reutilizam a consulta de sessão de `modules/auth/routes.ts` e revalidam conta/sessão na transação. Socket.IO valida sessão/CSRF no handshake e revalida sessão/conta antes de comandos, atualizações e periodicamente, sem renovar o prazo ocioso pelo heartbeat. Contratos comuns publicados ficam em `shared`, estados privados e motores na API. No frontend, compartilhar transporte, sincronização e componentes visuais comprovadamente comuns; tabuleiro, animações, ações disponíveis e cálculo exibido continuam nas features dos jogos.

Jogos com intervenções podem implementar `authorize(state, seat, action)` no driver. O executor continua verificando sessão, participação humana, versão e recibo; o driver valida a vaga autenticada e as ações legais, incluindo as de fora da vez. Os drivers sem essa capacidade mantêm a autorização pela decisão atual.

`deferredAutomaticMs` interrompe a cadeia síncrona de automações somente para os jogos que o declaram. O processo da API chama `advanceDeferredMatches` periodicamente: o intervalo usa `updated_at` persistido, locks `FOR UPDATE SKIP LOCKED` e uma única ação por sala vencida. Reinícios preservam o intervalo; múltiplas instâncias não repetem decisões. Salas sem automação aguardam a ação humana, sem timeout. Testes só com bots continuam usando avanço manual/reprodução de desenvolvimento. O Solo utiliza 2,4 segundos entre automações para permitir intervenções reais; o navegador apresenta o snapshot privado atual e não bloqueia essas intervenções por animações.

### Adicionar um jogo

1. Criar schemas de opções, ações e projeção pública em `packages/shared/src/<jogo>.ts`; exportar pelo índice. Registrar a definição e os schemas nas uniões de `game-registry.ts`. Definir valores iniciais, campos `select`/`switch`, dependências entre campos, limites por configuração e capacidades. A definição não contém segredos.
2. Implementar motor e driver em `apps/api/src/modules/games/<jogo>/` e registrar em `games/registry.ts`. Usar os drivers existentes como exemplos, sem copiar autenticação, SQL, lobby ou economia. `decision` informa vaga/chave de notificação; `projectFor` recebe somente a vaga ainda controlada pelo destinatário ou `null` para espectador. `outcome` informa vencedores e vagas humanas; o livro de Croins continua transacional na plataforma.
3. Implementar a apresentação em `apps/web/features/games/<jogo>/module.tsx`, seguindo `game-module.ts`, e registrar em `registry.tsx` e `server-registry.ts`. `Table` recebe estado confirmado, controles e função de comando; `Entry` compõe a entrada oficial quando suportada. O lobby lê os campos declarados, sem condições por jogo. Usar os componentes existentes de cartas/mesa apenas quando a apresentação e o comportamento forem comuns.
4. Validar o contrato: automação até decisão humana/fim, ações ilegais, autorização da vaga, duplicação, versões obsoletas, projeções por destinatário, abandono, reconexão e proteção dos eventos. Adicionar integração em banco exclusivo de teste e E2E da apresentação. Cadastrar o jogo no admin após registrar o código; liberar modo oficial/Croins/replay somente quando os respectivos fluxos estiverem implementados e revisados.

Para informação oculta, `snapshotOnly` recupera sempre a projeção atual por destinatário, sem reproduzir frames públicos como se fossem privados. `eventAction` deve remover escolhas sigilosas; os frames persistidos usam sempre a projeção de espectador. No Love Letter, ações nos eventos são marcadas como `step`, sem cartas privadas do Chanceler; recibos devolvem apenas confirmação. O Flip 7 mantém seus frames de apresentação e replay. Reconectar não executa motores nem reproduz ações no banco.

O contrato atual atende jogos de mesa/turnos, com 2–12 vagas e distribuição de pote entre vencedores. Solo é multiplayer e está restrito ao desenvolvimento; suas regras estão em [solo.md](solo.md). Jogos de um jogador, sem turnos, em tempo real contínuo ou com financiamento/distribuição distintos ainda exigem ampliar esses contratos a partir de um caso concreto. A pontuação do resumo é específica de cada jogo. Histórico/replay HTTP aceita projeções registradas; a apresentação administrativa de replay seleciona as mesas de Flip 7, Love Letter e Solo pelo estado registrado; um novo jogo com replay precisa integrar seu apresentador antes da liberação. Instalação/upload de código de usuários pelo site, isolamento de módulos externos e SDK publicado permanecem pendentes.

## Partidas integradas

- `modules/matches` executa o ciclo compartilhado; `modules/games/<jogo>` contém motor, invariantes privadas e driver. `games/cards.ts` fornece embaralhamento puro com RNG injetável; o driver usa `crypto.randomInt`, e testes podem usar seeds determinísticas.
- Migrations de partidas criam salas, participantes vinculados a contas, comandos e eventos. Migrations históricas do protótipo podem conter limpezas de development/test; já aplicadas, não devem ser reaplicadas em bases com dados reais. Criação usa `requestId` por criador; comandos usam `commandId` por conta/sala e `expectedVersion` nas decisões/início. Locks e recibos confirmam junto com o estado; host pode mudar sem perder a identidade do criador.
- `/api/v1/matches`: GET lista publicamente partidas em andamento; POST cria lobby. GET `/lobbies` lista salas abertas e identifica separadamente todos os lobbies da conta, suas criações próprias por jogo e sua primeira partida ativa, mesmo fora do limite das listagens públicas. GET `/:code` consulta publicamente lobby ou mesa, inclusive finalizada. POST `/:code/join`, `/leave`, `/start`, `/update` controlam o lobby; `/commands` aplica decisão de qualquer jogo registrado, `/abandon` transfere a vaga para bot e `/kick` permite expulsão pelo host no lobby ou jogo. As rotas antigas `/love-command` e `/love-abandon` são aliases de compatibilidade dos mesmos serviços; clientes novos usam as rotas comuns. Escritas usam sessão/Origin/CSRF. Uma conta pode ocupar vários lobbies e manter uma criação própria normal por jogo, considerando salas normais abertas e partidas normais em andamento. Partidas de desenvolvimento não entram nesse limite. Criação, entrada e início normais verificam ausência de outra vaga ativa do mesmo jogo sob seu controle; jogos diferentes podem ocorrer simultaneamente. As mutações de ciclo de vida adquirem um advisory lock transacional antes dos locks de conta e sala: o início pode remover vagas em várias salas e precisa serializar essas alterações entre processos, contas e abas. O primeiro início confirmado retira todos os participantes das demais filas do mesmo jogo, libera suas reservas, transfere hosts e fecha salas vazias na mesma transação; salas de outros jogos são preservadas.
- Capacidade é limite de 2–12 pessoas; iniciar requer host, versão atual e pelo menos duas contas ativas. O host pode alterar modalidade/Brutal/capacidade somente no lobby. Reduzir a capacidade remove as últimas vagas excedentes na ordem apresentada (participantes, convites e bots), preservando o host; os assentos restantes são compactados e a quantidade de bots é persistida na mesma transação. O cliente escolhe opções compatíveis a partir do registro público quando a quantidade exige outro modo; a API valida os limites do modo recebido. Configuração, expulsão, entrada/saída/início usam o mesmo lock da sala, recibos idempotentes e versões nas decisões do host. Ao sair, o host passa para o participante mais antigo ainda no controle; última saída fecha. Em partidas iniciadas, desconectar não retira vaga nem automatiza decisões; a política de expiração abaixo vale somente para lobbies. Abandono e exclusão de conta usam a mesma ordem de lock de ciclo de vida para não disputar transferências de host e remoções em várias salas. Exclusão de conta encerra suas salas/partidas para evitar vagas sem controlador.
- Cada decisão pertence à conta da vaga indicada pelo motor (`bonusChoice`, ação pendente ou turno). Host não controla os demais. Não há criação pública de convidados ou bots. Abandono/expulsão em jogo mantém identidade, cartas e pontos, remove o controlador da vaga no banco e a entrega a um bot normal; escolhas pendentes e automações continuam na mesma transação. Eventos `replace` registram a mudança antes das jogadas do bot. A conta removida perde o controle da vaga e pode continuar acompanhando como espectador. Sem humanos, a partida gratuita encerra como abandonada. Mesas iniciadas aceitam espectadores autenticados ou visitantes, sem comandos nem ocupação de vagas.
- Convites: host consulta `GET /:code/players?q=`, envia `POST /:code/invite` e compartilha o endereço público da sala. Unicidade por sala/destinatário torna repetição idempotente; convites válidos reservam capacidade e aparecem na projeção do lobby. Entrada consome a reserva; `POST /:code/decline` recusa e libera a vaga, e expulsão também permite remover reservas. Início exige ausência de convites pendentes e presença Socket.IO de todos os participantes no site, verificada na transação. Reservas e alterações da sala usam o mesmo lock para impedir superlotação. Envio exige sessão revalidada, host, sala aberta e alvo ativo, com limite de frequência. A requisição Socket.IO `presence` renova presença de 75 segundos e retorna convites válidos da conta; a interface chama a cada 15 segundos somente com página visível e recebe alterações de convites por evento, apresentando alertas com Aceitar/Recusar. `match_presence` mantém um lease de 30 segundos por conexão/sala para todas as salas ativas sob controle da conta enquanto mantém conexão autenticada no site, renovados a cada 15 segundos e removidos ao desconectar ou perder o controle da vaga. Navegar para outra página não remove a presença nem abandona a partida. Presença e convites ficam em PostgreSQL, sem inferir Online apenas pela existência de sessão.
- O executor resolve compras obrigatórias e passagem de rodada na transação até a próxima decisão humana ou fim. Eventos versionados e snapshots privados ficam no banco. Socket.IO envia mudanças da sala e listagens públicas de lobbies/partidas; conexões autenticadas também recebem retomada por conta, convites e `personal-matches`, com nome do catálogo, endereço, status, indicação de turno e participantes públicos (nome e avatar) de todas as posições das suas salas, incluindo bots previstos no lobby e bots da mesa iniciada. Esse resumo é exclusivo da conta, não contém cartas ou estado privado e é atualizado após commits apenas para participantes da sala afetada, independentemente da assinatura da mesa. Reconectar recupera a lista completa; conclusão ou perda do controle remove o atalho. Visitantes apenas observam, e a presença na sala só é registrada para participantes autenticados. Cada processo Fastify mantém um `LISTEN` PostgreSQL. A migration `0021_scoped_realtime` envia identificadores e tipos de alteração após commit: mesa, conta, convite, presença, autorização ou catálogo. O servidor consulta somente os domínios afetados e agrupa avisos pendentes por conexão, recuperando todos os eventos persistidos desde a versão confirmada. A mesa não assina listagens; o lobby assina listagens e a sala aberta. Jogadas comuns não refazem consultas de presença, convites ou diretórios. A listagem pública de partidas usa resumos (rodada, participantes e controladores), sem carregar cartas/histórico; atualiza em mudanças de rodada ou ciclo de vida. Uma manutenção a cada 15 segundos renova leases, remove presenças/convites vencidos e revalida sessões; remoções notificam os assinantes afetados, sem polling de jogadas. Assinaturas `watch` têm orçamento por identidade de 120 tentativas por minuto em cada processo, compartilhado entre suas conexões; recusas não prolongam a janela. Esse limite transitório não usa o bloqueio horário persistido das ações. `REALTIME_MAX_CONNECTIONS` controla o limite por processo (padrão 200); não representa capacidade medida. A confirmação do comando é um recibo, enquanto o evento `room` entrega os frames inclusive a quem enviou. Cada assinatura `watch` reenvia as listagens de lobbies e partidas quando solicitadas, mesmo sem alterações desde a assinatura anterior na mesma conexão global; a deduplicação vale para atualizações da assinatura atual. Reabertura/reconexão recupera eventos contíguos ou snapshot, com autorização e deduplicação por versão.
- Snapshot público inclui quantidade de cartas no baralho, nunca ordem/seed. Lista/retomada carregam no servidor Next. Cliente apresenta frames pela fila GSAP, restringe controles à própria decisão e bloqueia ações desconectado. LocalStorage guarda somente preferências; a economia das partidas é confirmada pela API.

Navegar para outra página, ocultar a aba ou perder a conexão não pausa o motor nem abandona a vaga. Automações confirmam até a próxima decisão humana; sem timeout, essa decisão aguarda seu controlador. Uma nova leitura da mesa usa snapshot confirmado, sem repetir eventos. A sincronização de uma mesa montada pode recuperar eventos contíguos; versão inválida, lacunas ou mais de mil eventos retornam snapshot. No cliente que apresenta animações, sequências completas de até 12 eventos podem ser animadas; sequências maiores ou recebidas com a aba oculta aplicam o snapshot. Isso não cancela imediatamente uma animação que já estava em execução ao ocultar a aba. Áudio em aba oculta é interrompido, sem retomada dos efeitos antigos. Esses limites de recuperação visual não são regras do motor.

Pendente: unificar a política de retomada visual e os contratos dos adaptadores de jogos. A infraestrutura compartilhada deve receber capacidades e operações do adaptador para configurar lobby, projetar estado por destinatário, identificar decisões, executar comandos e produzir resultados. Seleção de regras e de apresentação pertence ao registro dos jogos, sem ramificações por nome de jogo nos serviços comuns. Mesa, cartas, histórico e som podem compartilhar componentes configuráveis; regras, conteúdo privado e composição específica permanecem com cada jogo. Ao retornar de ausência, a direção proposta é descartar apresentações antigas e mostrar o estado confirmado, preservando animações para novas ações; a interface ainda precisa implementar e validar essa política.

### Expiração de lobbies

`modules/matches/lobby-maintenance.ts` executa a cada 15 segundos, inclusive sem sockets conectados, sob o lock transacional comum de ciclo de vida. A presença considera todas as conexões autenticadas da conta no site; navegar entre páginas mantém a vaga. Em lobby normal com alguém online, participantes offline por dois minutos são removidos e o host ausente é substituído pelo participante online mais antigo. Quando todos estão offline, as vagas são preservadas e a sala encerra após cinco minutos. Reconectar zera os prazos de ausência na próxima manutenção. A detecção e o processamento podem acrescentar até dois ciclos ao prazo observado; leases não renovados vencem em 30 segundos.

Lobbies normais avisam o host após 30 minutos e encerram dois minutos depois sem confirmação. O resumo privado `personal-matches` entrega o prazo somente ao host; `POST /:code/keep-open` e a requisição Socket.IO correspondente renovam por mais 30 minutos com dois minutos para resposta, com sessão revalidada, autorização do host e recibo idempotente. Início e renovação recusam prazo vencido. Lobbies de desenvolvimento não têm limite de duração nem removem participantes por ausência; encerram após 30 minutos com todos offline, incluindo o host observador de salas apenas com bots.

A migration incremental `0031_panoramic_iron_lad` deve ser aplicada antes da API. Salas existentes recebem o prazo a partir da implantação, sem fechamento retroativo. Ausências e prazo ficam persistidos; encerramento marca a sala como `abandoned` com motivo e remove convites/presença, preservando sala, participantes restantes, comandos e eventos. Não há cobrança nem devolução na expiração: a entrada só é cobrada no início. Partidas iniciadas e arquivos oficiais permanecem fora dessa manutenção. Para reverter a aplicação, manter a migration e os registros; não recriar salas já encerradas nem desfazer alterações de saldo.

### Partidas de desenvolvimento

`game_matches.development` identifica testes e é imutável. A página com `teste=1` exige sessão administrativa também no servidor Next e retorna 404 para as demais contas e visitantes. Convites levam à URL da partida sem esse parâmetro, permitindo participação autorizada sem acesso à ferramenta de desenvolvimento. A criação e o início exigem administrador ativo revalidado na transação; outras contas entram apenas por convite válido. A leitura exige host, participação ou convite válido, inclusive por Socket.IO. As listagens públicas excluem testes; `tests` e `testLobbies` alimentam a área de salas no modo dev. O switch “Modo dev” fica dentro do cabeçalho do jogo, no canto superior direito, e o badge “Desenvolvimento” acompanha o título; configurações, vagas e convites usam o mesmo componente do modo normal. Testes permitem várias salas e partidas simultâneas, inclusive do mesmo jogo, sem compartilhar o limite de criação do modo normal. Participação por convite mantém as permissões do modo de desenvolvimento. Cada sala pode ser cancelada inteira por seu administrador. O fluxo usa os mesmos lobbies, presença e convites das partidas normais, com indicação explícita de teste no alerta e na mesa.

`bots` define vagas automáticas e `only_bots` mantém o administrador como observador. Testes apenas com bots avançam por comandos administrativos versionados/idempotentes (`test-step`); a interface oferece reprodução e pausa, sem executar regras no navegador. Sair do lobby como host encerra o teste; `end-test` permite ao administrador da sala cancelar diretamente o teste inteiro, com confirmação na interface, inclusive com jogadores. Desenvolvimento não admite propostas coletivas. O abandono individual transfere a vaga para um bot e mantém a partida para os demais; mesmo sem humanos, os bots concluem a partida. O início de um teste não remove pessoas de lobbies normais.

Testes exigem entrada zero, não criam potes e não alimentam `game_match_archives`. Assim, não entram no histórico oficial, rankings, conquistas ou atividades do perfil. A migration incremental `0035_match_test_analysis` mantém arquivos independentes em `game_test_archives` e `game_test_archive_frames`, preservados após exclusão da conta ou da sala operacional. Apenas projeções de espectador e ações públicas são copiadas de `game_match_events`; mãos privadas, notas e escolhas sigilosas permanecem na API. O admin filtra a origem em Jogos → Partidas e consulta replay paginado dos dois jogos. Participantes e o administrador dono do teste podem rever partidas encerradas em `/me/matches/:code`; a consulta administrativa continua exigindo permissão de jogos.

O início e o encerramento são registrados no servidor em `game_matches`. Testes só com bots também acumulam tempo em reprodução por lease de 15 segundos, renovado pela interface a cada cinco segundos; pausa, ocultação e saída da tela suspendem a contagem, com tolerância máxima do lease se houver perda abrupta da conexão. O total inclui pausas; o tempo em reprodução acompanha o ritmo de apresentação, não representa benchmark do motor nem estimativa do tempo humano. Avanços manuais com reprodução pausada não acumulam esse relógio. A lista administrativa mostra médias de testes concluídos por jogo, opções, quantidade de jogadores e presença de humanos, com tamanho da amostra; cancelados e testes antigos sem datas conhecidas ficam fora das médias. A migration recupera os frames antigos ainda disponíveis sem inventar duração; partidas oficiais mantêm seus arquivos e datas. Aplicar a migration antes de publicar a API; recuperação usa rollback da aplicação mantendo as novas tabelas, colunas e históricos, sem desfazer a migration.

Aplicar a migration incremental `0029_development_matches` antes de publicar API/interface: partidas existentes recebem `development=false`, sem mudanças em saldos ou arquivos. A migration também cadastra Love Letter sem sobrescrever um cadastro existente. Para voltar a versão da aplicação, encerrar testes ativos e manter colunas, restrições e dados; não desfazer migrations nem apagar históricos. O Love Letter aceita somente desenvolvimento, mesmo se o catálogo estiver publicado. Regras e limites em [Love Letter](love-letter.md).

### Economia das partidas

`modules/matches/economy.ts` reutiliza `transferCroinsInTransaction`: aceites do valor ficam nas vagas do lobby, a cobrança é conjunta no início e a liquidação acompanha a transação que confirma o resultado. `game_match_stakes` mantém contribuições por carteira/vaga, conta do pote, total, distribuição e status; não tem FK para sala ou usuário, preservando auditoria após exclusões. O extrato e o histórico da conta já consultam os lançamentos do livro. A consulta administrativa cruza o arquivo independente com essa liquidação; nenhum snapshot privado é exposto. Regras em [Flip 7](flip7.md#economia).

A migration `0027` é incremental: salas existentes recebem entrada zero, sem cobranças retroativas. Aplicar antes de publicar API/interface que usam esses campos; não exige reset ou seed de contas reais. Exclusões de contas devolvem potes pendentes sob o lock de ciclo de vida antes da remoção; um trigger impede apagar sala com pote pendente por um caminho que esqueça essa etapa. Falhas operacionais anteriores ao commit revertem integralmente; retries retornam recibos já confirmados. Para reverter a aplicação, interromper a abertura de salas com entrada e concluir ou devolver todos os potes pendentes antes de voltar a uma versão sem suporte econômico; manter tabelas, operações e arquivos, sem migration destrutiva de reversão.

A migration incremental `0030_simple_frog_thor` adiciona `game_match_cancellations`, independente de contas e salas operacionais para preservar a auditoria. Propostas e votos HTTP usam sessão/CSRF e o lock de ciclo de vida, conta e sala; o servidor calcula elegibilidade por controladores ativos. Recibos em `game_match_commands` tornam retries idempotentes. A unanimidade confirma devoluções no livro, liquidação `refunded`, aprovação e encerramento na mesma transação. Falhas revertem tudo. Triggers fecham propostas quando um controlador muda ou a partida termina; resoluções são imutáveis. A publicação exige aplicar a migration antes da API. Reversão da aplicação mantém a tabela, votos e operações, sem desfazer devoluções.

### Histórico administrativo de partidas

Admin → Jogos → editar jogo lista partidas iniciadas, com busca por código/participante, status, modo, datas, pontuações e vencedores (incluindo empates). Partidas finalizadas também expõem `durationSeconds` no estado público, calculado entre início e término do arquivo existente, sem incluir espera no lobby; sem registro, retorna nulo. Não há relógio local nem migration para esse resumo. Lista e reprodução enriquecem os participantes com os nomes de exibição e avatares atuais em uma consulta em lote por página, usando username quando o nome estiver vazio e identidade arquivada quando a conta não existir. Essa apresentação não altera nomes/IDs nem frames arquivados. Contas removidas ou sem avatar usam fallback no frontend; não há cópia de imagens no arquivo nem migration. A reprodução tem início/final, avanço/retorno, pausa e velocidade, com paginação de frames. Controles só alteram a visualização; não executam comandos na mesa real. O acesso aos endpoints de histórico e reprodução exige admin na API, inclusive para jogos desativados.

`game_match_archives` e `game_match_archive_frames` preservam identidades por vaga, versão das regras e projeções públicas confirmadas. Triggers da migration `0023` registram os eventos na mesma transação da partida; rollback não publica histórico e repetição idempotente não duplica frames. Nenhum baralho privado ou seed é arquivado. A cópia independente não tem FK para usuário ou sala operacional, mantendo histórico após exclusões; remover uma sala em andamento a registra como encerrada sem vencedor. Resultados finalizados não são reescritos por exclusões. A exclusão de conta ainda encerra suas salas operacionais; o arquivo preserva seus registros.

A migration recupera históricos existentes, sem recriar registros já apagados. Para essas partidas antigas, início usa a criação da sala e término usa sua última atualização, pois não existiam timestamps específicos; novas partidas registram início na transição de lobby. `GET /api/v1/rankings` agrega o arquivo para vitórias e quantidade de derrotas (Flip 7 por pontuação final; Love Letter pelos vencedores finais), e carteiras para saldo atual em `modules/rankings/service.ts`. A consulta pública valida filtros/paginação, seleciona a posição da sessão fora da página e não expõe snapshots nem contas operacionais. Critérios em [Rankings](../CROEBET.md#44-rankings-e-gamificação). Não exige migration nem recalcula saldos.

## Próximas integrações

Priorizar a estabilização dos fluxos existentes antes de ampliar funcionalidades. Implementação e cobertura automatizada não substituem validação entre dispositivos nem ensaio de recuperação. Não criar estruturas antecipadamente só por constarem aqui.

1. Executar as verificações de [Validação](#validação), incluindo integração em banco exclusivo de test e E2E pertinentes. Validar lobbies e partidas entre dispositivos reais: navegação fora da mesa, múltiplos jogos, troca de aba, perda de conexão, retorno durante escolhas especiais e sincronização de apresentação/áudio. Mesas normais já aceitam espectadores; substituir uma vaga por outra conta continua indisponível. A expiração de lobbies está implementada, mas partidas iniciadas aguardam decisões humanas indefinidamente; qualquer timeout ou substituição automática por ausência exige decisão de produto. Essa espera também pode bloquear publicações pela proteção de partidas em andamento.
2. Validar a operação com Croins entre dispositivos e os cenários de concorrência, repetição e falha em banco exclusivo de test, conferindo entrada, pote, prêmio, empate, abandono e devolução. Regras implementadas em [Flip 7](flip7.md#economia).
3. Ensaiar a restauração de backup em destino isolado, conferindo contas, saldos, históricos e imagens, e manter cópia externa protegida. Procedimentos e limites de rollback em [Produção independente no Mac](#produção-independente-no-mac).
4. Para novas contribuições de jogos, seguir [Adicionar um jogo](#adicionar-um-jogo) e validar capacidades, privacidade, histórico e apresentação de replay antes de liberar cada recurso. O executor compartilhado já existe; SDK público e instalação de código pelo site continuam pendentes.
5. Quando as apostas públicas forem retomadas, integrar palpite/débito/pote, apuração e pagamento separados. Preservar [regras aprovadas](../CROEBET.md#42-apostas), pagamentos idempotentes e devoluções atômicas; não importar palpites locais. Recuperação sem e-mail continua em aberto. Conquistas e rankings usam os registros existentes; critérios específicos de ações dos jogos continuam futuros.
